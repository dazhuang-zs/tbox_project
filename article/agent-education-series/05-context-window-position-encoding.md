# 【AI Agent 系统教学 05】上下文窗口的奥秘

> 为什么 GPT-4 有 128K 上下文，但真的用到 128K 时反而变笨了？
> 为什么 Agent 在长对话中会"失忆"？
> 答案藏在位置编码和注意力分布里。

---

## 前言：Agent 的"记忆"去哪了

做 Agent 开发的人基本都遇到过这个场景：

第 1 轮对话，Agent 准确记住了用户的需求。
第 20 轮对话，Agent 开始"忘记"前面说过什么。
第 50 轮对话，Agent 甚至重复了前面已经回答过的问题。

表面上看是"上下文窗口不够大"。但即使换了大上下文窗口的模型，问题依然存在。

**为什么？**

因为上下文窗口虽是 Agent 的"工作记忆"，但在这个"记忆"里，信息不是均匀分布的。越靠前的信息，在 Attention 中越容易被稀释。

## 一、位置编码的演进

### 1.1 位置编码为什么重要？

如果没有位置编码，Transformer 中"猫追老鼠"和"鼠追老猫"的 Attention 计算结果完全一样。因为 Attention 只关心"谁和谁关联"，不关心"谁在什么位置"。

位置编码就是给模型提供位置信息的机制。

### 1.2 各代位置编码对比

| 位置编码 | 代表模型 | 核心思想 | 最大能力 | 长上下文扩展 |
|---------|---------|---------|---------|------------|
| Sinusoidal | Transformer 原版 | 固定正弦/余弦函数 | 理论无限 | 可以直接外推 |
| Learned | BERT、GPT-2 | 可训练的位置向量 | 训练时见过的最大长度 | 不行 |
| RoPE | Llama、Qwen、DeepSeek | 旋转 Q 和 K 向量 | 理论无限，但实际衰减 | NTK-aware 插值 |
| ALiBi | BLOOM、MPT | 给 Attention 加线性偏置 | 理论无限 | 天生支持 |
| YaRN | Llama 3 长上下文 | RoPE 的改进版 | 128K+ | 专门优化 |

### 1.3 RoPE 深度解析

RoPE（Rotary Position Embedding）是 2026 年最主流的位置编码，也是当前所有开源模型（Llama 3、Qwen 2.5、DeepSeek V3）的标准配置。

**核心思想**：对 Query 和 Key 向量进行旋转，旋转角度由位置决定。

```
位置 0 的 Q 向量：旋转 0 度
位置 1 的 Q 向量：旋转 θ 度
位置 2 的 Q 向量：旋转 2θ 度
...
位置 n 的 Q 向量：旋转 nθ 度
```

**为什么旋转有效**？

两个向量的点积受旋转角度差影响：
- 位置相近的 Q 和 K：旋转角度差小，点积大 → 注意力强
- 位置相远的 Q 和 K：旋转角度差大，点积小 → 注意力弱

**这就是 RoPE 的"相对位置编码"本质**：Attention 分数取决于 token 之间的相对位置，而不是绝对位置。

### 1.4 RoPE 的局限性

RoPE 有一个问题：**当位置距离很远时，Attention 分数会趋于零**。

```
相对距离 = 1：Attention 分数 ≈ 0.95
相对距离 = 10：Attention 分数 ≈ 0.70
相对距离 = 100：Attention 分数 ≈ 0.30
相对距离 = 1000：Attention 分数 ≈ 0.05
```

这意味着模型**天然倾向于关注附近的 token**。当上下文很长时，开头的 token 对当前生成的 token 几乎没有影响。

这就是为什么 128K 上下文模型在 128K 时表现不如 8K——不是因为模型"记不住"，而是因为远处的信息在 Attention 中占比太小。

## 二、长上下文扩展技术

### 2.1 位置编码插值（Position Interpolation）

**问题**：模型在 4096 长度的 RoPE 上训练，突然要处理 8192 长度的输入。RoPE 的旋转角度到了训练时未见过的范围，模型无法理解。

**解法**：把位置编码"拉伸"。

```
原始：位置 0-4096 → 旋转角度 0-4096θ
插值后：位置 0-8192 → 旋转角度 0-4096θ（位置 8192 的旋转角度"压缩"到位置 4096 的水平）
```

**效果**：模型可以处理更长的上下文，但精度略有损失（因为所有位置的角度"变近了"）。

### 2.2 NTK-aware 插值

**核心洞察**：不同频率的 RoPE 分量应该用不同的插值策略。

- 高频分量（捕捉局部信息）：几乎不插值，保持局部精度
- 低频分量（捕捉全局信息）：大幅插值，扩展到长距离

**效果**：比简单插值效果更好，长上下文能力提升更明显。

### 2.3 YaRN（Yet another RoPE extensioN method）

YaRN 是 Llama 3 长上下文版本使用的技术，核心改进：

1. **混合插值策略**：高频和低频用不同插值率
2. **温度缩放**：调整 Attention softmax 的温度，补偿长上下文带来的注意力分散
3. **短上下文微调**：用少量长上下文数据微调，让模型适应

**效果**：Llama 3 70B 从 8K 扩展到 128K，在长上下文基准测试中保持 90%+ 的准确率。

### 2.4 上下文窗口扩展技术对比

| 技术 | 实现复杂度 | 是否需要微调 | 效果 | 代表模型 |
|------|-----------|------------|------|---------|
| 直接外推 | 最简单 | 否 | 差（性能急剧下降） | 无 |
| 位置插值 | 简单 | 少量 | 中 | Code Llama |
| NTK-aware | 中等 | 少量 | 好 | Qwen 2.5 |
| YaRN | 中等 | 少量 | 很好 | Llama 3 |
| 长上下文微调 | 复杂 | 大量 | 最好 | GPT-4 |

## 三、长上下文时代的"麻烦"

### 3.1 困惑点（Lost in the Middle）

2023 年，一篇论文揭示了一个重要发现：

> **LLM 对上下文中间部分的信息处理能力，远低于开头和结尾。**

```
在上下文中搜索信息时：
  信息在开头（前 10%）：准确率 ~90%
  信息在中间（40-60%）：准确率 ~50%
  信息在结尾（后 10%）：准确率 ~85%
```

**这就是"Lost in the Middle"（迷失在中间）现象**。

**对 Agent 的影响**：

在 Agent 的多轮对话中：
- 最新几轮对话 → 在结尾 → 模型关注度高
- 历史对话 → 在中间 → 模型关注度低
- 系统指令 → 在开头 → 模型关注度高，但也会被遗忘

**这意味着**：即使有 128K 上下文，Agent 对中间部分的信息处理能力也是有限的。

### 3.2 注意力稀释

另一个长上下文的问题：**注意力资源是有限的**。

```
上下文长度 4K：每个新的 token 有 4096 个"注意力份额"
上下文长度 128K：每个新的 token 有 131072 个"注意力份额"
```

看起来份额更多了，但问题在于**这些份额要分配给更多的 token**。关键信息在 128K 上下文中的"信噪比"远低于 4K 上下文。

### 3.3 对 Agent 开发者的建议

**1. 不要贪上下文长度**

长上下文不是 Agent 的万能药。与其把所有信息塞进上下文，不如**精选**：

```python
# 错误做法
context = full_session_history  # 50K tokens

# 正确做法
context = recent_conversation(5 rounds) + summarize(earlier_history) + key_info
```

**2. 关键信息放在开头或结尾**

如果 Agent 需要记住某些信息，把它放在：
- < 模型训练时最大长度的一半（开头最容易被记住）
- 或紧接在用户最新输入之前（结尾最容易被记住）

**3. 显式提醒**

在上下文的关键位置加入显式标记：

```python
system_prompt += """
特别注意：以下信息非常重要，请务必记住：
<key_info>用户偏好：短回复，不要列点</key_info>
"""
```

**4. 外部记忆系统**

对于重要的长期信息，使用外部存储（向量数据库、记忆系统），而不是依赖上下文窗口。

## 四、2026 年的上下文窗口现状

### 4.1 主流模型对比

| 模型 | 最大上下文 | 有效使用长度 | 位置编码 |
|------|----------|------------|---------|
| GPT-4o | 128K | 64K | 推测 RoPE 变体 |
| Claude 3.5 Sonnet | 200K | 100K | 推测 RoPE 变体 |
| Gemini 1.5 Pro | 2M | 500K | 推测 RoPE + 稀疏注意力 |
| Llama 3 70B | 128K | 64K | YaRN |
| Qwen 2.5 72B | 128K | 64K | NTK-aware |
| DeepSeek V3 | 128K | 96K | RoPE + 改进 |

**注意"有效使用长度"**：这是实际测试中模型能保持较高准确率的最大长度，远低于官方宣称的最大值。

### 4.2 百万级上下文的真正意义

2026 年，Gemini 1.5 Pro 宣称 2M token 上下文，Qwen 2.5 也达到 1M。但实际使用中有几个关键问题：

**问题 1：检索效率**

当上下文达到百万级，模型对这些信息的"检索"能力远不如专门的检索系统（向量数据库）。即使模型"看到"了信息，也未必能"找到"。

**问题 2：计算成本**

百万级上下文的一次推理，计算量和显存需求都是天文数字。即使技术上可行，成本上也不现实。

**问题 3：信息密度**

百万级上下文中的大部分信息，对当前任务可能毫无帮助。模型需要从中筛选出有用信息——这本身就是一个难题。

**百万级上下文的真正价值不在于"记住所有信息"，而在于"不需要外部检索系统"的场景**——比如分析整本书、处理整个代码库。

## 五、Agent 的上下文管理策略

### 5.1 上下文窗口管理

```
┌──────────────────────────────────────────────────┐
│ System Prompt  │ 早期对话  │ 中期对话  │ 当前对话 │
│   （固定）      │  （压缩）  │  （压缩）  │  （完整）  │
└──────────────────────────────────────────────────┘
```

**分区域管理**：

| 区域 | 内容 | 管理策略 |
|------|------|---------|
| System Prompt | 角色设定、工具定义 | 固定，不变 |
| 早期对话 | 多轮前的历史 | 摘要压缩 |
| 中期对话 | 近期的历史 | 选择性保留 |
| 当前对话 | 当前正在进行的交互 | 完整保留 |

### 5.2 上下文压缩技术

**1. 摘要压缩**

```python
def summarize_history(history):
    prompt = f"请用 100 token 以内总结以下对话：\n{history}"
    return llm(prompt)
```

**2. 选择性保留**

只保留与当前任务相关的历史对话：

```python
def relevant_history(history, current_query):
    # 只保留与当前查询相关的对话轮次
    return [turn for turn in history if is_relevant(turn, current_query)]
```

**3. 结构化记忆**

把历史对话中的关键信息提取成结构化格式：

```python
memory = {
    "user_preferences": {"style": "concise", "language": "Python"},
    "completed_tasks": ["task_weather_query", "task_email_send"],
    "current_project": "AI Agent tutorial",
    "key_decisions": [
        {"decision": "use LangGraph", "reason": "state machine needed"}
    ]
}
```

### 5.3 上下文预算

给每个部分分配 token 预算：

```python
CONTEXT_BUDGET = {
    "system_prompt": 2000,     # 工具定义、角色设定
    "recent_conversation": 4000,  # 最近 3-5 轮
    "compressed_history": 1000,   # 历史对话的摘要
    "memory_summary": 500,       # 关键记忆
    "tool_results": 2000,        # 工具调用结果
    "current_input": 1000,       # 当前用户输入
}
```

**为什么要做预算**？因为不控制，上下文会无限增长。预算给了你一个明确的"分配逻辑"——超过预算时，决定压缩什么。

## 总结

| 概念 | 一句话 | 对 Agent 的影响 |
|------|--------|----------------|
| 位置编码 | 给 token 打上位置标签 | 决定了模型能处理多长的上下文 |
| RoPE | 当前主流的位置编码 | 天然倾向于关注近处的 token |
| Lost in the Middle | 中间信息容易被忽略 | 关键信息要放在开头或结尾 |
| 注意力稀释 | 上下文越长，关键信息越不突出 | 不要贪长上下文 |
| 上下文压缩 | 用摘要替代原始内容 | 核心的 Agent 上下文管理手段 |

**Agent 开发者需要记住的核心原则**：上下文窗口不是记忆，而是工作台。工作台有限，你需要决定放什么上去。
