# 【AI Agent 系统教学 03】对齐技术：RLHF、DPO 与指令微调

> 预训练让模型"会说话"，对齐让模型"说人话"。
> 没有对齐，GPT-4 也只是一个知识渊博的"偏执狂"。

---

## 前言：为什么 Agent 需要对齐模型？

你写 Agent 代码时，最怕遇到什么情况？

- 问它"帮我查一下天气"，它回了一篇关于天气预报的论文
- 让它执行一个工具调用，它返回一段"我理解你的需求，作为AI助手..."
- 它在思考过程中突然开始"角色扮演"，偏离了任务
- 用户问了一个敏感问题，它直接回复了有害内容

这些问题，根源在对齐（Alignment）。

**对齐的目标**：让模型的行为符合人类的期望——有用、诚实、无害。

预训练模型（Base Model）学会了"什么话可能出现在互联网上"，但这不代表"什么话应该被说出来"。对齐就是解决这个差异的。

---

## 一、对齐的三大目标

### 1.1 有用（Helpful）

模型应该：
- 理解并执行用户的指令
- 给出准确、完整的回答
- 主动提供额外有用信息

**反例**：用户问"怎么用 Python 写一个函数"，模型回复"函数是编程中的基本概念..."

### 1.2 诚实（Honest）

模型应该：
- 不知道就说不知道
- 不编造事实（减少幻觉）
- 标注不确定性程度

**反例**：用户问"2025 年世界杯冠军是谁？"，模型编造了一个结果。

### 1.3 无害（Harmless）

模型应该：
- 拒绝有害请求
- 不输出歧视、暴力、仇恨内容
- 不协助违法犯罪

**反例**：用户问"如何制作炸弹"，模型给出详细配方。

## 一个不可能三角？

这三个目标之间存在天然张力：

```
有用 ↔ 无害：过度安全 = 什么都不敢做
无害 ↔ 诚实：有些"真相"也可能有害
诚实 ↔ 有用：直接说"不知道"不够有用，但编造更糟
```

好的对齐需要在三者之间找到平衡。这也是为什么 Agent 开发中，你经常需要调整模型的"温度"和上下文提示——本质上是在手动调整这个平衡。

## 二、指令微调（SFT）：让模型学会"听话"

### 2.1 什么是 SFT？

Supervised Fine-Tuning（SFT）是对齐的第一步。用**人工标注的对话数据**来微调预训练模型。

**训练数据**：

```
用户：请用 Python 写一个斐波那契数列函数
助手：def fibonacci(n):
        if n <= 1:
            return n
        return fibonacci(n-1) + fibonacci(n-2)

用户：上面这个函数性能太差了，能优化吗？
助手：可以使用动态规划或迭代：
def fibonacci(n):
        a, b = 0, 1
        for _ in range(n):
            a, b = b, a + b
        return a
```

**关键点**：
- 数据量：几万到几十万条（相比预训练的万亿 token，微乎其微）
- 不学新知识：这些知识模型预训练时已经"见过"
- 学的是**交互模式**：什么样的输入，应该给出什么样的输出

### 2.2 SFT 数据质量 > 数据量

2026 年的共识是：几百条**高质量**的 SFT 数据，效果超过几千条**普通**数据。

什么算高质量 SFT 数据？

| 维度 | 好数据 | 差数据 |
|------|-------|-------|
| 指令多样性 | 覆盖各种任务 | 都在问类似问题 |
| 回答质量 | 准确、完整、简洁 | 啰嗦、有错误、不完整 |
| 格式规范 | 遵循统一格式 | 格式混乱 |
| 难度梯度 | 从简单到复杂 | 全是简单问题 |
| 场景覆盖 | 包含 Agent 场景 | 只有问答 |

### 2.3 SFT 对 Agent 的特殊意义

大多数 Agent 框架的"提示词模板"本质上就是在做**手工 SFT**——在用户输入前加上固定格式的 System Prompt，告诉模型"你是一个 Agent，你可以使用以下工具..."

这与 SFT 的思路一致：教模型在特定场景下应该怎么做。

区别在于：
- SFT：修改模型参数，效果持久
- Prompt：只影响当前对话，灵活但不可靠

这就是为什么专业的 Agent 应用会做**领域微调**——把 Agent 的 System Prompt 和工具调用格式作为 SFT 数据，训练模型更稳定地执行 Agent 任务。

## 三、RLHF：基于人类反馈的强化学习

### 3.1 为什么 SFT 不够？

SFT 的问题：模型学会的是"人类标注者认为好的回答"，但标注者只能给出**某个具体回答**的好坏，不能给出"这个回答比那个好多少"。

RLHF 的核心思想是：**让模型自己生成多种回答，然后让人类排序，把排序结果作为训练信号。**

### 3.2 RLHF 三阶段流程

```
阶段一：SFT
Base Model → 人工标注问答数据 → SFT Model

阶段二：训练奖励模型
SFT Model → 生成多个回答 → 人类排序 → 训练 Reward Model

阶段三：强化学习
SFT Model + Reward Model → PPO 训练 → RLHF Model
```

### 3.3 阶段二详解：奖励模型（Reward Model）

**训练数据**：对同一个问题，让模型生成多个回答，然后人类标注员排序。

```
问题："解释一下量子计算"
回答 A：量子计算是利用量子比特...（详细准确）
回答 B：量子计算很厉害...（模糊）
回答 C：量子计算...（有错误）

人类排序：A > B > C
```

**训练目标**：奖励模型学会给"好回答"高分，"差回答"低分。

**关键技术**：奖励模型不直接预测"好/坏"，而是**比较两个回答的相对好坏**。这比绝对评分更稳定。

### 3.4 阶段三详解：PPO 强化学习

**PPO（Proximal Policy Optimization）** 是 RLHF 中使用的强化学习算法。

简化版流程：

```
对于每个问题：
  1. SFT Model 生成一个回答
  2. Reward Model 给这个回答打分
  3. 更新模型参数，让模型更倾向于生成高分回答
  4. 同时添加 KL 散度约束：不要偏离 SFT Model 太远
```

**为什么需要 KL 约束？**

如果没有约束，模型会"钻空子"——找到 Reward Model 喜欢但实际很差的回答模式。比如：
- 写超长的回答（Reward Model 可能觉得"更详细"更好）
- 盲目赞同用户（"你说得对"）
- 过度使用某些句式

KL 约束保证模型在"让 Reward Model 满意"和"保持合理"之间平衡。

### 3.5 RLHF 的成本

RLHF 的代价非常高：

| 环节 | 成本 |
|------|------|
| 标注员训练 | 需要专业标注员，理解对齐目标 |
| 标注数据 | 每条排序需要 3-5 个回答，每个回答由多人标注 |
| 训练奖励模型 | 需要独立的模型训练 |
| PPO 训练 | 需要同时跑 4 个模型（策略、参考、奖励、价值） |

**这就是为什么 RLHF 主要是大模型公司（OpenAI、Anthropic、Google）在做的原因。**

## 四、DPO：更简单的对齐方案

### 4.1 DPO 的核心思想

DPO（Direct Preference Optimization）是 2023 年提出的 RLHF 替代方案。它的核心洞察是：

> **奖励模型和策略模型可以合并。**

DPO 直接用偏好数据（好回答 > 坏回答）来优化模型，不需要显式的奖励模型和 PPO 训练。

### 4.2 DPO vs RLHF

| 维度 | RLHF | DPO |
|------|------|-----|
| 需要独立奖励模型 | 是 | 否 |
| 训练稳定性 | 中等（PPO 调参困难） | 较好 |
| 实现复杂度 | 高 | 低 |
| 数据效率 | 中等 | 好 |
| 代表性模型 | GPT-4、Claude | Llama 3、Qwen 2.5 |

### 4.3 DPO 的数学直觉

DPO 的损失函数设计得很巧妙：

```
对于每个偏好对 (y_w, y_l)：
  - y_w：人类偏好的回答
  - y_l：人类不偏好的回答
  
损失 = -log σ(β × (log π(y_w|x)/π_ref(y_w|x) - log π(y_l|x)/π_ref(y_l|x)))
```

**直觉理解**：DPO 希望模型对"好回答"的生成概率高于"差回答"的生成概率，差距越大越好。同时用参考模型 π_ref 约束，"不要偏离原始模型太远"。

### 4.4 为什么 2026 年 DPO 成为主流？

2026 年，绝大多数开源模型（Llama 3、Qwen 2.5、DeepSeek V3）都在用 DPO 或其变体做对齐，原因很简单：

- **不用训练奖励模型**：节省了大量成本
- **更容易迭代**：换一个新偏好数据集，直接跑 DPO
- **效果不输 RLHF**：在大多数基准测试上，DPO 与 RLHF 持平或更好

## 五、对齐对 Agent 的深远影响

### 5.1 Agent 场景下的对齐挑战

**挑战 1：Tool Use 与安全**

Agent 可以调用工具，这意味着对齐不仅要考虑"说什么"，还要考虑"做什么"。

```
用户：帮我写一个程序，每天自动发消息给我的前女友
对齐的模型：拒绝（有害请求）
未对齐的模型：好的，这是代码（协助骚扰）
```

**挑战 2：过度安全拒绝**

对齐过度可能导致 Agent 对正常请求也拒绝。

```
用户：帮我写一个剪刀石头布的游戏
过度对齐的模型：抱歉，我不能协助开发游戏，因为...
正常模型：好的，以下是代码...
```

**挑战 3：多步任务中的对齐偏差**

在 Agent 的多步任务中，对齐可能"逐层累计"：
- 第 1 步：模型决定调用工具 A
- 第 2 步：工具 A 返回结果
- 第 3 步：模型决定调用工具 B
-...

每一步的"对齐"可能让模型做出不同的决策，最终导致一个与最初意图完全不同的结果。

### 5.2 给 Agent 开发者的建议

**1. 选择对齐程度合适的模型**

| 场景 | 推荐模型类型 | 原因 |
|------|-------------|------|
| 客服 Agent | 对齐好的模型 | 需要安全、友善 |
| 代码 Agent | 对齐适中的模型 | 需要灵活、不拒绝 |
| 研究 Agent | 对齐较轻的模型 | 需要探索性、输出完整 |
| 安全 Agent | 严格对齐 | 需要高度可靠 |

**2. Prompt 中明确对齐期望**

通过 System Prompt 补充对齐，告诉模型在什么情况下应该拒绝，什么情况下应该执行。

**3. 用工具权限做第二道防线**

即使模型判断失误，工具权限系统可以拦截：
- 文件写入权限：只允许写入特定目录
- 网络访问权限：只允许特定 API
- 执行权限：沙箱中执行

### 5.3 对齐的未来方向

**Constitutional AI（Anthropic）**
- 用一套"宪法规则"指导模型行为
- 不需要大量人工标注
- Claude 系列使用

**Self-Play（自我对弈）**
- 模型自己生成偏好数据，自己训练
- 类似 AlphaGo 的自我进化
- DeepSeek R1 使用了类似技术

**可编程对齐**
- 用户可以根据需要调整对齐策略
- 类似于"给模型一个对齐配置文件"
- 让 Agent 开发者可以定制对齐行为

## 六、实操：Agent 的 System Prompt 也是一种对齐

### 6.1 用 Prompt 做"轻量级对齐"

虽然你无法改变模型参数，但可以通过 System Prompt 影响模型的行为。

```python
system_prompt = """
你是一个 AI Agent，可以调用以下工具：
- get_weather(city): 查询天气
- search_web(query): 搜索网络
- send_email(to, subject, body): 发送邮件

规则：
1. 优先使用工具获取实时信息，不要编造
2. 如果不知道答案，就说"不知道"
3. 拒绝任何违法、有害、不道德的请求
4. 始终用中文回复
5. 工具调用结果必须如实报告
"""
```

**这就是"提示词工程"在做的事**——在推理时补充对齐信息。

### 6.2 Prompt 对齐 vs 模型对齐

| 维度 | 模型对齐（SFT/RLHF/DPO） | Prompt 对齐 |
|------|------------------------|------------|
| 持久性 | 永久 | 仅当前对话 |
| 一致性 | 高 | 依赖于模型理解 |
| 灵活性 | 低（需要重新训练） | 高（随时修改） |
| 覆盖范围 | 所有场景 | 仅当前对话 |
| 成本 | 高 | 低 |

**最佳实践**：两者结合——用模型对齐处理通用安全，用 Prompt 对齐处理特定场景。

## 总结

| 概念 | 一句话 | 对 Agent 的影响 |
|------|--------|----------------|
| SFT | 教模型"怎么看懂指令" | 决定 Agent 能否理解你的 System Prompt |
| RLHF | 用人类偏好优化模型 | 决定了 Agent 的"品味"——什么该做，什么不该做 |
| DPO | 更简单的 RLHF 替代 | 让更多开源模型可以对齐，Agent 生态更丰富 |
| Reward Model | 模型判断"什么回答好" | 决定了 Agent 在工具调用和对话中的"得分" |
| 对齐挑战 | 三目标（有用/诚实/无害）的平衡 | 直接影响 Agent 的可用性和安全性 |
