# 【AI Agent 系统教学 06】大模型的能力边界

> 不是所有模型都是全能的。知道模型能做什么，更要清楚它不能做什么。
> 对 Agent 开发者来说，理解能力边界就是理解"什么时候相信模型，什么时候加防护"。

---

## 前言：你的 Agent 到底靠不靠谱？

你写了一个 Agent，调用了 GPT-4o 的 API，试了 5 个例子都完美运行。你很开心，部署到生产环境。

然后：

- 第 100 个用户问了一个奇怪的问题，Agent 开始胡言乱语
- 第 200 个用户让 Agent 算 3 位数乘法，结果错了
- 第 500 个用户发现 Agent 在"编造"引用来源
- 第 1000 个用户问了一个 2026 年 6 月的事件，Agent 说不知道

这些不是 bug。**这是模型的能力边界**。

理解这些边界，不是让你对模型失望，而是让你知道**什么时候该相信模型，什么时候该加防护**。

---

## 一、涌现能力：什么时候模型突然"会了"

### 1.1 什么是涌现能力

涌现能力是模型规模达到某个阈值后，**突然出现**的能力。不是"逐渐变好"，而是"从无到有"。

| 能力 | 小模型（<1B） | 中模型（7B-13B） | 大模型（70B+） | 超大模型（200B+） |
|------|-------------|----------------|---------------|-----------------|
| 基础问答 | 不稳定 | 基本可用 | 可靠 | 很可靠 |
| 指令遵循 | 几乎不行 | 有限 | 良好 | 优秀 |
| 上下文学习 | 微弱 | 弱 | 可用 | 强 |
| 思维链推理 | 无 | 开始出现 | 良好 | 强 |
| 工具调用 | 无 | 不稳定 | 基本可用 | 可靠 |
| 自我纠错 | 无 | 无 | 有限 | 可用 |
| 代码生成 | 片段 | 简单函数 | 项目级 | 架构级 |

### 1.2 涌现能力的阈值

涌现不是魔法，它和模型的两个特性有关：

**能力组合**：复杂任务需要多个子能力的组合。小模型可能拥有子能力 A，但缺子能力 B，所以做不了。当模型大到同时拥有 A 和 B，任务突然能完成。

**注意力资源**：大模型有更多 Attention Head，可以同时关注多种信息。小模型"看过"但"记不住"——不是没学到，是注意力不够用。

### 1.3 对 Agent 的启示

**不要假设小模型能做到大模型的事。** 如果你在 7B 模型上看到 Agent 工具调用不稳定，这不是你代码的问题，是模型能力不够。

**但是，小模型也有自己的优势**：
- 速度快（本地部署，延迟低）
- 成本低（免费或极低成本）
- 隐私好（数据不出本地）

**正确做法**：根据任务复杂度选择模型，简单任务用小模型，复杂任务用大模型。

## 二、推理能力：模型真的会"思考"吗？

### 2.1 模拟推理 vs 真正推理

2026 年的共识是：**LLM 的推理本质上是"模式匹配 + 模拟推理"，而不是人类意义上的"逻辑推理"。**

```
问题：小明有 5 个苹果，吃了 2 个，又买了 3 个，现在有几个？
模型的计算过程：
1. 在训练数据中见过大量"苹果加减"的问题
2. 匹配到"初始数量 - 吃掉 + 买来"的模式
3. 输出：5 - 2 + 3 = 6
```

这不是人类的"推理"，而是**基于模式的模拟**。

### 2.2 推理能力的边界

**LLM 擅长的事**：
- 常见数学题（训练数据中大量出现）
- 常识推理（"下雨了所以要带伞"）
- 类比推理（"这个和那个类似，所以..."）
- 一步推理（直接得出结论）

**LLM 不擅长的事**：
- 多步逻辑推理（超过 5 步的推理链）
- 反事实推理（"如果历史是..."）
- 需要精确计算的数学（3 位数乘法可能错）
- 需要一致性的推理（同样的问题，换个问法答案不同）

### 2.3 思维链（CoT）的作用

思维链让模型"显式输出推理过程"，之所以有效，是因为：

1. **把"多步推理"变成"多步生成"**：每一步生成一个中间 token，每一步都比较简单
2. **利用因果注意力的特性**：前面的推理结果成为后面步骤的上下文
3. **减少"跳跃"错误**：显式推理让错误更容易被发现和纠正

### 2.4 对 Agent 的启示

**永远不要假设 Agent 的推理是正确的。** 特别是多步推理，每一步都可能出错。

**防护策略**：
1. 要求 Agent 输出推理过程（CoT），方便调试
2. 对关键步骤做验证（比如调用计算结果用计算器工具）
3. 设置重试逻辑（如果结果不合理，让 Agent 重新推理）
4. 使用"投票"机制（让模型多次推理，取多数结果）

## 三、幻觉：模型为什么"瞎编"？

### 3.1 幻觉的本质

幻觉不是 bug，是**模型的工作方式**。模型在训练时学到的核心能力是"生成概率最高的下一个 token"，而不是"说出事实"。

```
用户：2025 年诺贝尔物理学奖得主是谁？
模型：...让我想想...
模型在训练数据中见过：
  - "2024 年诺贝尔物理学奖得主是..."
  - "2023 年诺贝尔物理学奖得主是..."
  - "2025 年 XX 会议在..."
模型没有"知道"2025 年诺贝尔奖信息，但训练数据中存在"年份 + 诺贝尔奖 + 人物"的模式。
模型基于这个模式，生成了一个看起来合理但可能错误的答案。
```

### 3.2 幻觉的分类

| 类型 | 表现 | 原因 | 例子 |
|------|------|------|------|
| 知识幻觉 | 编造事实 | 训练数据中不存在该知识 | 编造一本不存在的书 |
| 源幻觉 | 引用错误来源 | 混淆了不同来源 | 把 A 论文的结果说成 B 论文的 |
| 逻辑幻觉 | 推理错误 | 推理链断裂 | 前提正确但结论错误 |
| 指令幻觉 | 曲解用户意图 | 对指令理解有偏差 | 用户要"翻译"但模型给了"解释" |

### 3.3 幻觉率与模型规模

| 模型 | 幻觉率（通用知识） | 幻觉率（专业知识） |
|------|------------------|------------------|
| GPT-4o | 3-5% | 10-15% |
| Claude 3.5 | 3-5% | 10-15% |
| Llama 3 70B | 5-8% | 15-20% |
| Qwen 2.5 72B | 5-8% | 15-20% |
| 7B 模型 | 10-15% | 20-30%+ |

**注意**：这些是"不安全"的保守估计。在特定领域（如公司内部知识），幻觉率可能更高。

### 3.4 Agent 场景下的幻觉应对

**策略 1：工具优先**

对于任何需要事实信息的场景，工具优先于模型知识：

```python
# 错误做法
agent.respond("2026年世界杯冠军是谁？")  # 模型可能瞎编

# 正确做法
agent.respond("搜索2026年世界杯冠军，然后告诉我")  # 强制使用搜索工具
```

**策略 2：验证循环**

Agent 生成结果后，让另一个 Agent 或工具验证：

```python
result = agent.respond("生成一份关于 Transformer 的总结")
# 验证步骤
verify_prompt = f"请验证以下内容是否有事实错误：\n{result}"
verified = verifier_agent.respond(verify_prompt)
```

**策略 3：不确定时坦白**

在 System Prompt 中明确要求模型在不确定时承认：

```python
system_prompt = """
如果你不确定某个信息，请说"我不确定"。
如果你在编造，请停止。
优先使用工具获取信息。
""""
```

**策略 4：RAG 增强**

用 RAG 提供事实基础，减少模型依赖内部知识：

```python
# 检索相关文档
docs = retriever.retrieve(user_query, k=5)
# 注入上下文
context = "\n".join(docs)
prompt = f"基于以下信息回答问题：\n{context}\n\n问题：{user_query}"
```

## 四、知识截止：模型知道什么时候的事？

### 4.1 知识截止日期

每个模型都有一个知识截止日期——训练数据中最新数据的时间点。

| 模型 | 知识截止日期 |
|------|-------------|
| GPT-4o | 2024 年 10 月 |
| Claude 3.5 | 2024 年 4 月 |
| Llama 3 | 2023 年 12 月 |
| DeepSeek V3 | 2024 年 6 月 |
| Qwen 2.5 | 2024 年 3 月 |

**这是模型最硬的能力边界**。模型"不知道"截止日期之后的任何事件。

### 4.2 知识截止 vs 幻觉

这是 Agent 场景中最常见的"坑"：用户问一个截止日期之后的问题，模型不知道，但也不说"不知道"，而是基于训练数据中的模式"编造"一个答案。

```
用户：2026 年 7 月有哪些重要的 AI 会议？
模型的知识截止：2024 年 10 月
模型处理：
  1. 知道"XX年 AI 会议"的模式
  2. 知道 2024、2025 年的会议信息
  3. 基于模式"推测"2026 年的会议
  4. 输出看起来合理的信息
  5. 但其中可能包含过期信息或编造内容
```

### 4.3 应对策略

**对于需要最新信息的问题，强制使用工具**：

```python
# 不依赖模型内部知识
agent.respond("请搜索 2026 年 7 月的 AI 会议信息")

# 或在 System Prompt 中明确
system_prompt += """
注意：你的知识截止于 2024 年 10 月。
对于任何 2024 年 10 月之后的事件，请使用搜索工具获取信息。
不要凭记忆回答。
"""
```

## 五、模型的可控性

### 5.1 可控性的维度

| 维度 | 说明 | 实际操作 |
|------|------|---------|
| 格式可控 | 能否按指定格式输出 | JSON、XML、Markdown 格式约束 |
| 行为可控 | 能否按指定行为执行 | 是否调用工具、是否思考 |
| 内容可控 | 能否控制输出内容 | 指定语气、长度、风格 |
| 安全可控 | 能否拒绝有害请求 | 拒绝攻击、敏感内容 |

### 5.2 格式约束的可靠性

| 约束方式 | 7B 模型 | 70B 模型 | 200B+ 模型 |
|---------|--------|---------|-----------|
| 口头要求"输出 JSON" | 30% 可靠 | 70% 可靠 | 95% 可靠 |
| 给 JSON 示例 | 50% 可靠 | 85% 可靠 | 98% 可靠 |
| 约束解码 | 99% 可靠 | 99% 可靠 | 99% 可靠 |

**约束解码（Constrained Decoding）** 是确保格式输出的最可靠方式——在 token 生成时直接限制只能输出符合格式的 token。

### 5.3 对 Agent 的启示

**不要依赖模型"自觉"遵守格式约束。** 对于需要严格格式的输出（如劲具调用 JSON），使用约束解码或用代码后处理验证。

## 六、能力边界总结

### 6.1 一张表看完

| 能力 | 大模型能做 | 但需要注意 |
|------|----------|----------|
| 问答 | 通用知识准确 | 专业领域可能出错 |
| 推理 | 常见推理模式有效 | 多步推理可能断裂 |
| 代码 | 常见编程任务 | 复杂逻辑可能引入 bug |
| 工具调用 | 单步工具基本可靠 | 多步工具链不稳定 |
| 记忆 | 上下文窗口内 | 中间信息易丢失 |
| 格式 | 常见格式 | 需要约束解码保证 |
| 安全 | 基本无害 | 对抗攻击可能突破 |

### 6.2 Agent 开发者的能力边界检查清单

在写 Agent 代码时，逐个问自己：

- [ ] 这个任务在模型的能力范围内吗？（如果要求 7B 模型写复杂 Agent，可能不行）
- [ ] 如果模型犯错，后果有多严重？（设置保护措施）
- [ ] 模型需要"事实"还是"推理"？（需要事实 → 用工具或 RAG）
- [ ] 这个信息在模型的知识截止日期之后吗？（强制使用搜索工具）
- [ ] 格式要求严格吗？（考虑约束解码）
- [ ] 需要多步推理吗？（每一步增加验证）

## 总结

| 能力边界 | 本质 | 对 Agent 的启示 |
|---------|------|----------------|
| 涌现能力 | 阈值效应，大模型能做小模型做不了的事 | 量力而行，复杂任务用大模型 |
| 推理能力 | 模式匹配，不是真正的逻辑推理 | 多步推理加验证，不要完全信任 |
| 幻觉 | 模型的"生成"本能，不是 bug | 工具优先，RAG 增强，验证循环 |
| 知识截止 | 训练数据的时间边界 | 过期问题强制搜索 |
| 可控性 | 模型越大越可控，但永远不完美 | 约束解码 + 后处理验证 |

**你的 Agent 不可能比它底层的模型更聪明。** 理解模型的能力边界，就是理解 Agent 的能力上限。在这个范围内设计，才是务实的 Agent 开发。
