# Agent 记忆系统的三种记忆：短期、长期和工作记忆

人的记忆分三种。

你在开车时突然想起「今晚要买菜」，这是**短期记忆**在工作。你不需要翻笔记就知道红灯要停，这是**长期记忆**。而你在倒车入库时同时关注后视镜、方向盘角度、旁边车的距离——这是**工作记忆**在协调。

Agent 的记忆系统，正在往同一个方向走。不是巧合，是必然。

---

## 一个让你立刻有感觉的例子

这是我上个月调的一个 Agent。任务是帮用户查 CSDN 文章数据，然后生成一份周报。

第一轮对话是这样的：

```
用户：帮我看看这周我发了哪些文章，数据怎么样
Agent：好的，我先查一下...你本周发了 3 篇文章，总阅读量 5800
用户：跟上个月同期比呢？
Agent：我需要查一下上个月的数据...
```

Agent 调了 API，查到了数据。没问题。

但到了第三轮：

```
用户：把涨得最快的那篇分析一下，看看为什么火
Agent：好的。让我查一下这篇文章的数据...
（又调了一次 API，重新查了一遍刚才已经查过的数据）
```

它没有记住——第二轮的查询结果，到第三轮就「忘」了。

这就是没有短期记忆的后果。Agent 不会「记住刚才查过什么」，每一轮对话都像第一次见面。

## 三种记忆各解决什么问题

**短期记忆**：刚才发生了什么。

在 Agent 里，短期记忆 = Context Window。当前对话的所有消息——用户说的、AI 回的、工具调用的结果——都在里面。

问题是：Context Window 有上限。Claude 200K，GPT-4 128K，看着很大对吧？但你跑一个中等复杂度的 Agent 任务：

```
System Prompt:    2,000 Token
工具描述:          1,500 Token
RAG 检索结果:      3,000 Token
对话历史（3轮）:    2,500 Token
工具返回（每次）:    500-2,000 Token
────────────────────────────
单轮: ~9,000 Token
十轮: ~90,000 Token
```

128K 的窗口以为够用，十轮对话就快满了。满了之后最前面被截断的是什么？是你最精心写的 System Prompt——Agent 的「人格设定」和「安全规则」最先被忘记。

**长期记忆**：以前学过的东西。

在 Agent 里，长期记忆 = 向量数据库。存进去的知识不会因对话结束而丢失。下一轮对话开始时，Agent 可以从向量库里检索到「三个月前用户说过他喜欢 Python 方案而不是 Java」这类信息。

但长期记忆也有局限：检索精度。纯向量检索的命中率大约 70-75%。这意味着 100 次检索中有 25-30 次返回的不是最佳匹配。对于 Agent 来说，一次检索失败就可能让整个任务走偏。

**工作记忆**：此刻正在处理的信息。

在 Agent 里，工作记忆 = 当前任务状态。Agent 正在执行一个多步骤任务——第一步查了天气，第二步算了价格，第三步要结合前两步的结果给出建议。它需要同时「看到」第一步和第二步的结果来做出第三步的判断。

这就是为什么 ReAct 模式每次都要把之前的思考（Thought）和执行结果（Observation）放回对话历史——不是因为它啰嗦，是因为它需要工作记忆来跨步骤推理。

## 我踩过的三个坑

**坑一：把短期记忆当长期记忆用**

最早搭 Agent 的时候，我把所有东西都往 Context Window 里塞——用户偏好、项目背景、技术栈选择、常见问题。每次对话都带 3000 Token 的 System Prompt。

后果很明显：十轮对话后 Agent 开始「失忆」。不是模型不行，是我把它的短期记忆当硬盘用了。

后来拆开了——System Prompt 只放行为规则（200 Token 以内），知识放向量库，对话历史定期摘要。

**坑二：以为向量检索能替代结构化查询**

Agent 需要记住「用户 A 的 API Key 是 sk-xxx」这种精确信息。我最初用向量库存，结果好几次检索回了相似的但不准确的结果——比如查「用户 A 的 API Key」返回了「用户 B 的 API 配置说明」。

向量检索做语义匹配很强，但做精确匹配很弱。这种结构化数据应该用 SQL 查，不是用语义搜。

**坑三：多步骤任务中丢失中间状态**

有一次 Agent 需要按顺序做三件事：查订单 → 算折扣 → 生成发票。前两步正常，第三步时 Agent 把第一步查到的订单号忘了——因为前两轮的对话历史已经在第三步时被工具返回的 4000 字结果挤出了 Context Window。

解决方法很简单：关键信息在每步开始时重新声明一次。但当时没意识到，以为是模型的问题，反复换模型都没用。

## 怎么设计这三种记忆

**短期记忆**：把 Context Window 当宝贵资源用

```
优先级排序（从高到低）：
1. System Prompt 的核心规则（永远不被截断）            ~200 Token
2. 当前任务的关键中间状态（订单号、用户ID等）            ~500 Token
3. 最近 3 轮对话的摘要（不是全文，是摘要）              ~500 Token
4. 从长期记忆中检索到的相关片段                        ~1500 Token
────────────────────────────────────────────
预留安全空间（总窗口的 20%）                           ~20,000 Token
```

定期做摘要——每 5 轮对话，让 Agent 自己生成一个「目前为止发生了什么」的摘要，然后把原始对话历史替换成摘要版。

**长期记忆**：分层存储

```
结构化数据（精确查询） → SQL / 关系型数据库
  用户ID、API Key、项目配置、偏好设置

非结构化数据（语义查询） → 向量数据库
  历史对话摘要、技术文档片段、决策记录

需要两者结合的（最常见） → 向量 + SQL 混合
  先向量搜「用户A关于数据库的讨论」
  再用 SQL 精确查「用户A的数据库配置」
```

**工作记忆**：关键信息不依赖对话历史传递

多步骤任务中，不要把步骤 1 的结果只放在对话历史里。用 `scratchpad`——一个在 Agent 循环外部维护的状态对象：

```python
scratchpad = {
    "order_id": None,      # 步骤1填入
    "total_amount": None,   # 步骤2填入
    "invoice_url": None     # 步骤3填入
}
```

每步执行后更新 scratchpad，每步开始时先读 scratchpad。这样即使 Context Window 满了导致早期对话被截断，关键中间状态也不会丢失。

## 不是三种技术，是一种设计思维

把这三种记忆拆开看，每种的实现都不复杂。真正难的是意识到「Agent 需要记忆系统」这件事本身。

大多数 Agent 教程会教你怎么调 Function Calling、怎么用 LangChain。但不会告诉你 Agent 最大的问题不是「工具选错了」或者「Prompt 没写好」，而是「它不记得它自己刚才做了什么」。

三种记忆的核心区别就一句话：**短期记忆管「刚才」、长期记忆管「以前」、工作记忆管「现在」**。三者缺一不可——缺短期记忆，Agent 健忘；缺长期记忆，Agent 无知；缺工作记忆，Agent 断片。
