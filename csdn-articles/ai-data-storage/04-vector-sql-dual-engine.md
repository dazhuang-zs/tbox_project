# 向量数据库 + 关系型数据库 = Agent 的「双引擎」——为什么单靠 RAG 不够

我有一个用了半年的 Agent，专门帮我整理技术笔记。它的工作流程很简单：我丢给它一篇文章或一段对话，它提取关键知识点，存起来，以后我需要的时候帮我检索。

前三个月它表现得还不错。但后来我发现一个问题：当你问它「我那个关于数据库连接池的笔记在哪里」时，它十次有七次能找到。但当你问它「数据库连接池的最大连接数我设置的是多少」时，它几乎每次都找不对。

前一个是语义问题，后一个是精确查询。向量数据库擅长前者，关系型数据库擅长后者。但我的 Agent 只有向量数据库。

---

## 什么时候向量检索会翻车

向量检索的弱点不是「找不到」，是「找不精确」。

你向量化了「数据库连接池最大连接数应该设多少」，它会返回你所有关于连接池的笔记——包括怎么配置 HikariCP、连接超时怎么处理、连接泄漏怎么排查。但它很难精确返回那个数字：50。

因为向量数据库做的是**近似匹配**，不是**精确查询**。它返回的是「和你的查询最相似的前K条」，而不是「和你的查询完全匹配的那一条」。

还有两个更隐蔽的问题：

**数字和日期查询**。向量对「2026年3月」的理解是模糊的——它可能把「2026年3月」和「2026年2月」排在一起，因为它们语义上很接近。但日期查询需要精确到天，向量做不了。

**结构化过滤**。你想查「我在 CSDN 上写过的所有关于数据库的文章，按阅读量排序」。向量的语义搜索能帮你找到「关于数据库」的内容，但「按阅读量排序」这个操作需要在结构化数据上完成。

---

## 双引擎长什么样

不是要你抛弃向量数据库——它仍然是 Agent 记忆系统不可或缺的一半。但另一半需要关系型数据库来兜底。

```
Agent 查询
    │
    ├─ 语义检索（向量数据库）          ← 负责「这个内容和我问的相不相关」
    │   └─ 适合：开放式问题、概念查询、找出相关上下文
    │
    └─ 精确查询（关系型数据库）        ← 负责「这个值是多少」
        └─ 适合：数字查询、日期范围、排序、过滤、聚合
```

在实际的 Agent 流程里，这两种查询不是先后关系，而是**同时进行然后融合结果**。

比如我问 Agent：「我在 2026 年 3 月写的关于 Agent 调试的文章里，LangFuse 的内存泄漏怎么解决的？」

Agent 需要同时做两件事：
- 向量检索：「Agent 调试」「LangFuse 内存泄漏」→ 找到相关的文章片段
- SQL 查询：`SELECT * FROM articles WHERE date BETWEEN '2026-03-01' AND '2026-03-31' ORDER BY date DESC`

然后取两个结果集的交集——既语义相关又在 3 月份写的文章。

## 混合检索不是新概念，但 Agent 场景下有新挑战

混合检索（Hybrid Search）在信息检索领域已经用了很多年。向量 + BM25 关键词匹配，RRF 融合，Cross-Encoder 重排序——这套流程是标准的。

但在 Agent 场景下多了一个问题：**检索结果的质量直接决定了 Agent 的回答质量，但 Agent 自己不知道检索结果的好坏。**

它不是搜索引擎——搜索引擎给用户展示 10 条结果，用户可以自己判断哪条有用。Agent 是自动取前几条结果喂给 LLM，然后 LLM 基于这不完美的检索结果生成回答。如果前 3 条里有 1 条是错的或不相关的，LLM 的回答就会偏离。

这就是为什么 Agent 的混合检索不能只做「向量 + BM25」，还需要加一层「验证」。在把检索结果喂给 LLM 之前，让 LLM 自己快速检查一下——「这 3 条内容是否都和用户问题直接相关？」——如果有一两条不相关，先排除再生成回答。

这个额外的验证步骤会多烧一点 Token，但对于 Agent 来说，输出准确比省 Token 重要得多。

## 怎么在 Agent 里落地

不需要引入新的数据库。大部分 Agent 项目已经同时有这两个东西了——向量库用来做 RAG，SQL 数据库用来存业务数据。只需要在你的 Agent 流程里加一层「查询路由」。

```python
def route_query(question: str) -> str:
    """判断查询应该走哪条路"""
    if contains_exact_lookup(question):
        return "sql"          # 精确查询：数字、日期、ID
    elif contains_semantic_lookup(question):
        return "vector"       # 语义查询：概念、话题
    else:
        return "hybrid"       # 混合：先各取Top-10，再RRF融合
```

判断逻辑不复杂——检测查询中是否有数字、日期、特定 ID 格式（如 `sk-xxx`、`ORDER-12345`），有就优先走 SQL。

如果你只有向量数据库，加一个 SQLite 就行。不需要 MySQL 或 PostgreSQL——SQLite 一个文件就能跑，天然适合个人开发者或小团队。用 `sqlite-vec` 扩展甚至可以在 SQLite 里直接做向量检索，连外部向量数据库都省了。

---

双引擎不是什么新概念，但大多数 Agent 开发者还在用「用向量搜索一下然后喂给 LLM」这种单引擎模式。不是因为技术难，是因为还没意识到单引擎的局限性。当你开始把 Agent 用在真场景里——不是 Demo 不是 Hackathon——你会发现，「找不精确」这个问题的严重程度远超过「找不到」。
