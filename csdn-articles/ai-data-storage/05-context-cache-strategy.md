# AI 编程工具的上下文管理，本质上是一个缓存淘汰问题

你可能没从这个角度想过。

Claude Code 的 Context Window 200K Token。看着是个很大的池子，对吧？但你不是只用一次。你一天可能开 5-10 个对话，每个对话从两句变成几百句，每次都在往这个池子里倒东西。池子满了怎么办？倒掉最旧的？还是倒掉你觉得最不重要的？还是随机倒？

这个问题在计算机系统里有一个经典的解题框架：**缓存淘汰策略。**

---

## Context Window 就是一个缓存

把 Context Window 看成 CPU 的 L1 缓存——容量极小，速度极快，存的是当前最需要的数据。

LLM 推理 = CPU 运算。Context Window = 缓存。向量数据库 = 主存。文件系统 = 硬盘。

这个类比不只是有趣，它直接告诉你该怎么设计 Agent 的上下文管理策略。

| 缓存层 | 容量 | 速度 | 存储内容 |
|--------|------|------|------|
| Context Window | 200K Token | 即时（已在 GPU 显存中） | 当前对话 + 当前任务的检索结果 |
| 向量数据库 | 百万级条 | 毫秒级检索 | 历史知识、文档片段 |
| 文件系统 | 无限 | 慢（需要 I/O） | 原始代码、原始文档 |

每次 Agent 需要一段知识时，它应该像 CPU 查缓存一样：先查 Context Window（L1），找不到查向量数据库（主存），还找不到去读文件系统（硬盘）。

问题是：当 L1 缓存满了，该淘汰谁？

---

## 三种淘汰策略，三种不同的失败模式

**LRU（最近最少使用）**

把最久没用的内容踢出 Context Window。这是 CPU 缓存最常用的策略。

在 Agent 场景下会出什么问题？

你可能跟 Agent 聊了 20 轮都是关于前端的事，偶尔提了一下「对了我们的后端是 FastAPI」。这个「FastAPI」的信息在整个对话中只用了一次，按 LRU 它很快就会被踢掉。但它是上下文中最不应该丢失的东西之一——因为它是全局信息，不是局部信息。

LRU 在 Agent 场景下的问题就在这里：它假设「最近不用的 = 不重要的」，但 Agent 对话中，重要信息的使用频率往往极低。你的技术栈、你的数据模型、你的约束条件——这些全局信息可能一整轮对话只被引用一次，但丢失了后果很严重。

**LFU（最不经常使用）**

把使用频率最低的内容踢掉。

这更糟糕。全局信息使用频率最低——Agent 不会每句话都引用你的技术栈。按 LFU 策略，全局信息会第一个被踢出缓存。然后 Agent 就开始「忘记」你的项目背景，生成的代码风格完全不匹配。

**分层淘汰（我自己在用的）**

把 Context Window 里的内容分成三层，每层用不同的淘汰策略：

```
第1层：System Prompt 核心规则       → 永不淘汰
  行为约束、安全规则、输出格式
  这部分是 Agent 的「出厂设置」

第2层：全局上下文                  → 手动标记，不自动淘汰
  项目技术栈、用户偏好、关键架构决策
  这部分不到万不得已不踢

第3层：临时上下文                  → LRU 淘汰
  对话历史、工具返回、检索结果
  这部分是真正可以按时间淘汰的
```

实现不复杂。在每次往 Context Window 追加内容时，标记它属于哪一层。当总 Token 量超过 80% 窗口上限时，自动对第 3 层做 LRU 淘汰。当超过 90% 时，对第 2 层做摘要压缩（不是删除，是压缩成更短的形式）。

## 摘要比删除更好

我在第二篇文章里提到过，但值得单独展开说。

当 Context Window 满的时候，大多数人的做法是「删掉最旧的消息」。但这等于把 Agent 的记忆挖了一个洞。

更好的做法是**摘要**。让 Agent 自己把即将被淘汰的对话历史压缩成一段摘要，然后把摘要保留在 Context Window 里。

```
原始对话（2000 Token）：
用户：帮我看看这个 Bug
Agent：好的，让我看一下代码...（省略）
用户：是不是内存泄漏？
Agent：有可能，让我检查一下...（省略）
用户：找到原因了吗？
Agent：是的，是因为...（省略）

摘要（200 Token）：
讨论了 src/auth/routes.py 的内存泄漏问题。根因是 SQLAlchemy Session 没有在 finally 块中 close。修复方案：在 get_db() 函数中加 try-finally 确保 Session 被正确释放。
```

2000 Token 被压缩到 200 Token，信息没有丢失——Agent 仍然知道刚才发生了什么，只是细节被抽象了。

这不是什么新技术。人脑做的就是同样的事——你不会记住今天每一分钟的细节，但你会记住「今天解决了那个内存泄漏问题，原因是 Session 没关」。

## 缓存预热：启动时就加载关键信息

CPU 有缓存预热，Agent 也应该有。

当你启动一个新的 Claude Code 会话时，它应该一开始就知道：
- 你在做什么项目
- 项目的技术栈是什么
- 你个人有什么偏好（Python 还是 TypeScript）

而这些信息不应该靠你每次手动说一遍。

这就是 CLAUDE.md 的作用——但它太静态了。CLAUDE.md 里面写的是「本项目使用 FastAPI + SQLAlchemy」，但不会写「上个月你做了一个架构决策：放弃自研 Embedding，改用 BGE-Large-ZH，因为推理延迟从 800ms 降到 50ms」。

后面这类信息才是真正值钱的一类——**决策记录**。它比「项目用什么技术栈」重要得多，因为它是你在相似场景下做决策的依据。

我的做法很简单：每次做一个重要的技术决策后，记一行。

```markdown
2026-05: 放弃自研 Embedding → BGE-Large-ZH | 原因：延迟 800ms→50ms
2026-04: Milvus → Chroma（开发阶段切换） | 原因：部署太重
2026-03: REST API → MCP 协议接入 | 原因：标准化工具接口
```

每次启动 Claude Code 时，自动检索跟当前项目最相关的 5 条决策记录，注入到对话开头。

## 缓存问题不是 AI 专属问题

计算机系统发展了七十年，缓存管理已经是一门成熟的工程学科。LRU、LFU、分层淘汰、写回、写透——这些概念不是 AI 发明的，但 AI 的 Context Window 面临的问题和 CPU 缓存完全同构。

只不过 AI 社区大部分时间在讨论「怎么把 Context Window 做大」，而不是「怎么把现有的管理好」。做大当然有用，200K 总比 4K 好。但 200K 也有满的一天。

好的上下文管理 = 增量存储 + 自动摘要 + 分层淘汰。CPU 缓存工程师用了几十年才把这三件事做对。Agent 开发者只需要意识到：Context Window 不是无限内存，是有上限的缓存。管好比做大更重要。
