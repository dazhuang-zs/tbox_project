# 数据库索引原理：B+ 树为什么是最优解

> 面试必问：「MySQL 索引为什么用 B+ 树而不用 B 树？」答不上来的话，这篇文章值得收藏。

---

## 一、先搞清楚：没有索引时怎么查

假设 `users` 表有 100 万条数据，执行：

```sql
SELECT * FROM users WHERE email = 'user@example.com';
```

没有索引时，MySQL 一行一行扫过去，直到找到匹配的行——这就是「全表扫描」。最坏情况要读 100 万行。

> 你能想到的最朴素优化是什么？——排序后二分查找，O(log n)。

没错，这正是索引的核心思想。但磁盘上的「二分查找」比内存中复杂得多，因为磁盘 I/O 是按「页」（Page，默认 16KB）读取的，不是按行。

---

## 二、从二分查找到 B 树

### 2.1 二叉搜索树为什么不行

```
        [50]
       /    \
    [30]    [70]
    /  \    /  \
 [20] [40] [60] [80]
```

极端情况下（插入有序数据 1,2,3,4,5…），二叉搜索树会退化成链表：

```
[1] → [2] → [3] → [4] → [5] ...
```

查找复杂度 O(n)，和全表扫描一样。

### 2.2 平衡二叉树（AVL）行吗？

AVL 树解决了退化问题，但有两个致命缺陷：

- **树太高**：100 万条数据，树高约 20 层 → 每次查询要 20 次磁盘 I/O
- **一个节点只存一行**：16KB 的磁盘页，只放一行数据，严重浪费

> 磁盘 I/O 是数据库查询的最大瓶颈。一次 I/O 约 5-10ms，20 次就是 100-200ms。而内存操作是纳秒级。

---

## 三、B 树：为磁盘而生

B 树的核心思想就一个：**让每个节点存储更多数据，把树变矮**。

```
          [20 | 50 | 80]               ← 一个节点存多个 key
         /    |    |    \
    [5|10] [30|40] [60|70] [90|100]    ← 子节点
    /  |  \  ...
```

**B 树的规则**（m 阶 B 树）：

1. 每个节点最多 m 个孩子
2. 每个节点（除根外）至少有 ⌈m/2⌉ 个孩子
3. 所有叶子在同一层

以 MySQL 默认的 16KB 页大小为例，一个 B 树节点可以存储约 **1000 个键值**（取决于键的大小）。100 万条数据的 B 树高度大约是：

```
log_1000(1,000,000) ≈ 2
```

**只需要 2-3 次磁盘 I/O！**

---

## 四、B+ 树：B 树的进化版

MySQL InnoDB 用的是 B+ 树。它和 B 树只有两个关键区别，但这两个区别是决定性的。

### 区别 1：所有数据都在叶子节点

```
B树：
       [K|*|K|*|K]     ← 非叶子节点也存数据指针 (*)
      /    |    \
    叶子...              ← 叶子也有数据

B+树：
       [K|P|K|P|K]     ← 非叶子节点只存 Key + 子节点指针 (P)
      /    |    \
    [K|D][K|D][K|D]    ← 只有叶子节点存数据 (D)
```

### 区别 2：叶子节点通过指针串联

```
叶子节点：[K|D] → [K|D] → [K|D] → [K|D]
            ↑                              ↑
         链表头                         链表尾
```

---

## 五、为什么 B+ 树是最优解

### 5.1 非叶子节点存更多 key → 树更矮

B 树非叶子节点存了数据，占空间。同样 16KB 页，B+ 树的非叶子节点能存更多索引键，分叉更多，树高更小。

| 对比维度 | B 树 | B+ 树 |
|---------|------|-------|
| 100 万数据树高 | ~3 层 | ~2 层 |
| 非叶子节点内容 | Key + Data | 纯 Key |
| 单个节点可存 key 数 | ~500 | ~1200 |
| 范围查询 | 需要中序遍历回溯 | 叶子链表直接遍历 |

### 5.2 范围查询性能碾压

```sql
SELECT * FROM orders WHERE amount BETWEEN 100 AND 500;
```

- **B 树**：找到 100 的叶子后，需要沿着树的中序遍历来回跳，可能在叶子和非叶子之间反复切换
- **B+ 树**：找到 100 的叶子后，**顺着链表直接往后扫**，直到超过 500。顺序 I/O，快得多

这是 B+ 树最重要的优势——**范围查询在叶子链表上顺序扫描，充分利用磁盘预读**。

### 5.3 更适合磁盘 I/O 特性

磁盘有「预读」机制：读一个扇区时，会把相邻数据也读进缓存。

B+ 树的叶子节点紧密排列在磁盘上，范围扫描时整体顺序读取，完美利用预读。B 树的数据散落在各层节点中，随机 I/O 多。

## 六、用图说话：InnoDB 的 B+ 树长什么样

```
                   ┌─────────────────────┐
                   │   [500]  [1000]     │  ← 根节点（常驻内存）
                   │   P1     P2     P3  │
                   └──┬──────┬──────┬───┘
          ┌──────────┘      │      └──────────────┐
          ▼                 ▼                     ▼
┌─────────────────┐ ┌──────────────┐ ┌──────────────────┐
│ [100] [200]     │ │ [600] [700]  │ │ [1200] [1500]    │ ← 非叶子节点
│ P1  P2  P3     │ │ P1  P2  P3  │ │ P1   P2   P3     │
└──┬───┬───┬────┘ └──┬───┬──┬──┘ └──┬────┬────┬────┘
   ▼   ▼   ▼         ▼   ▼  ▼       ▼    ▼    ▼
┌────────────────────────────────────────────────────┐
│ [1]→[100]→[200]→[500]→[600]→[700]→[1000]→[1200]→[...]│ ← 叶子层（双向链表）
└────────────────────────────────────────────────────┘
```

### 聚簇索引 vs 二级索引

InnoDB 的**聚簇索引**（主键索引）的叶子节点直接存储整行数据：

```
聚簇索引叶子：[主键值 | 整行数据]
```

**二级索引**（普通索引）的叶子节点存储主键值：

```
二级索引叶子：[索引值 | 主键值]
```

这就解释了「**回表**」：通过二级索引找到主键值后，还要回到聚簇索引拿完整数据。

```sql
SELECT * FROM users WHERE email = 'test@example.com';
-- email 是二级索引 → 从 email 索引拿到主键 id → 回到主键索引拿整行
```

这就是为什么有时候 MySQL 选择全表扫描也不走索引——当回表成本太高时，全表扫描反而更快。

## 七、B+ 树 vs LSM 树

如果你用过 MongoDB 或者听说过 RocksDB，可能知道 LSM 树。简单对比：

| 维度 | B+ 树 (MySQL InnoDB) | LSM 树 (RocksDB/LevelDB) |
|------|---------------------|--------------------------|
| 写入性能 | 随机写入，需要分裂合并 | 顺序写入 WAL，极快 |
| 读取性能 | 2-3 次 I/O，快且稳定 | 可能需要查多层，较慢 |
| 写放大 | 有（页分裂） | 有（Compaction） |
| 适用场景 | 读多写少，OLTP | 写多读少，时序数据，日志 |

> 为什么 MySQL 不用 LSM？因为 MySQL 是 OLTP 数据库，读操作远多于写操作，B+ 树的读性能优势不可替代。

## 八、面试高频追问

### Q1：B+ 树一个节点存多少数据？

以 BigInt 主键（8 字节）+ 指针（6 字节）为例：

```
16KB / (8 + 6) ≈ 1170 个键值
```

三层结构：1170 × 1170 × 16 ≈ **2000 万行**数据只需 3 层，也就是 3 次 I/O。

### Q2：为什么不用 Hash 索引？

Hash 索引 O(1) 看起来更快，但：
- ❌ 不支持范围查询（`BETWEEN`、`>`、`<`）
- ❌ 不支持排序（`ORDER BY`）
- ❌ 不支持部分匹配（`LIKE 'abc%'`）
- ❌ Hash 冲突时退化
- ✅ 只适合等值查询（`=`、`IN`）

所以 InnoDB 的自适应 Hash 索引（AHI）只是 B+ 树的补充，而非替代。

### Q3：联合索引的「最左前缀」怎么理解？

```sql
INDEX idx_abc (a, b, c)
```

| 查询条件 | 是否命中索引 |
|---------|:---:|
| `WHERE a = 1` | ✅ |
| `WHERE a = 1 AND b = 2` | ✅ |
| `WHERE a = 1 AND c = 3` | ✅（只用 a） |
| `WHERE b = 2` | ❌ |
| `WHERE b = 2 AND c = 3` | ❌ |
| `WHERE c = 3` | ❌ |

B+ 树按 `(a, b, c)` 的顺序排列，跳过 a 直接查 b，索引就失效了。这就是上一篇慢查询优化中把 `status` 放在 `created_at` 前面的原因。

---

## 九、总结

```
为什么 B+ 树是数据库索引的最优解？

1. 树矮 —— 非叶子不存数据，同 16KB 页能存更多分叉，1000 万数据只需 3 层
2. 范围快 —— 叶子节点组成有序链表，范围查询顺序 I/O，完美利用磁盘预读
3. 稳定 —— 所有查询都走到叶子层，查询时间可预测（不像 B 树可能在中间节点命中）
4. 易管理 —— 所有数据在叶子层，分裂合并操作比 B 树简单
```
