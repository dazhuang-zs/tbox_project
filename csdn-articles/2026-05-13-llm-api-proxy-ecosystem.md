# 2026年LLM API中转站技术全景：从one-api到new-api，开源生态如何撑起一个行业

> **摘要**：当你打开任何一个AI API中转平台，背后大概率跑着同一套开源代码。本文从技术视角拆解one-api → new-api的演进脉络、核心架构、二次开发路径，以及所有搭建者绕不开的合规问题。

---

## 开篇：为什么市面上的API中转站都"长得很像"？

如果你用过市面上的AI API中转服务，可能会发现一个有趣的现象：它们的后台界面、Key管理方式、额度统计逻辑高度相似——有的甚至连默认密码都没改。

这背后是一个已经十分成熟的开源生态。今天我们从纯技术角度，拆解这个生态是怎么运转的。

---

## 一、基座：one-api，一个项目定义了一个品类

### 1.1 它解决了什么问题？

每个大模型厂商都有自己的API格式。OpenAI是一套、Claude是另一套、通义千问又是一套。对开发者来说，对接5个模型就要写5套代码。

**songquanpeng/one-api**（GitHub 18K+ Star，Go语言）的核心设计：

> 把所有模型提供商的API统一转成OpenAI格式，对外暴露一个标准Endpoint，开发者一行代码不用改。

支持的模型列表（截至2026年5月）：

| 类别 | 覆盖厂商 |
|------|---------|
| 海外主流 | OpenAI、Anthropic Claude、Google Gemini、Mistral、Groq、Cohere、xAI |
| 国内主流 | DeepSeek、通义千问、文心一言、讯飞星火、ChatGLM、豆包、腾讯混元、360智脑、Moonshot、百川、MiniMax、零一万物、阶跃星辰 |
| 其他 | Ollama（本地模型）、Cloudflare Workers AI、together.ai、novita.ai、硅基流动 |

### 1.2 核心功能一览

```
┌─────────────────────────────────────────┐
│              one-api 核心能力              │
├─────────────────────────────────────────┤
│ 🔑 Key 管理    │ 生成/分发/过期/额度控制    │
│ 📊 渠道管理    │ 批量创建、分组、模型映射   │
│ ⚖️ 负载均衡    │ 多Key轮询、失败自动重试    │
│ 💰 额度系统    │ 用户额度、兑换码、邀请返佣  │
│ 📈 日志监控    │ 请求日志、额度明细、报警    │
│ 🔐 权限控制    │ IP白名单、Token分组、模型限制│
│ 🌐 多格式输出  │ OpenAI/Claude/Gemini格式    │
└─────────────────────────────────────────┘
```

### 1.3 一键部署

```bash
# SQLite版（小规模使用）
docker run --name one-api -d --restart always -p 3000:3000 \
  -e TZ=Asia/Shanghai \
  -v /home/ubuntu/data/one-api:/data \
  justsong/one-api

# MySQL版（生产环境）
docker run --name one-api -d --restart always -p 3000:3000 \
  -e SQL_DSN="root:123456@tcp(localhost:3306)/oneapi" \
  -e TZ=Asia/Shanghai \
  -v /home/ubuntu/data/one-api:/data \
  justsong/one-api
```

访问 `http://localhost:3000`，默认账号 `root`，密码 `123456`。

> ⚠️ 官方文档明确警告：**生产环境务必修改默认密码**。然而事实上，大量公开暴露的中转站连这一步都没做。

## 二、进化：new-api，一个"二开"如何超越原版

### 2.1 从 Fork 到独立品牌

**new-api**（QuantumNous/new-api）是基于 one-api 的二次开发版本，目前在功能上已经大幅超越原版。它不是简单的"换个皮"，而是针对生产级场景做了系统性增强。

**原版 one-api 没有，new-api 新增的核心能力：**

| 维度 | one-api 原版 | new-api 增强 |
|------|-------------|-------------|
| **租户管理** | 无 | 组织级多租户隔离 |
| **计费粒度** | 简单额度扣减 | 按请求/按Token/按缓存命中分别计费 |
| **支付集成** | 无内置 | EPay、Stripe内置充值 |
| **缓存计费** | 不支持 | OpenAI/Azure/DeepSeek/Claude缓存单独计费 |
| **登录方式** | 邮箱/GitHub/飞书 | +Discord +Telegram +LinuxDO +OIDC |
| **API格式** | 仅OpenAI格式 | OpenAI + Claude原生 + Gemini原生 |
| **数据可视化** | 基础 | 仪表盘、统计分析 |
| **文档体系** | GitHub README | 完整的多语言独立文档站 |

### 2.2 技术架构示意

```
┌──────────────────────────────────────────────────┐
│                    用户请求                        │
│        POST /v1/chat/completions                  │
│        Authorization: Bearer sk-xxx               │
└──────────────────┬───────────────────────────────┘
                   │
                   ▼
┌──────────────────────────────────────────────────┐
│                  Nginx 反向代理                    │
│            域名 + HTTPS + 限流                    │
└──────────────────┬───────────────────────────────┘
                   │
                   ▼
┌──────────────────────────────────────────────────┐
│              new-api (Go, 端口3000)                │
│  ┌──────────┐ ┌──────────┐ ┌──────────────────┐  │
│  │ Token验证 │ │ 额度检查  │ │ 渠道路由+负载均衡 │  │
│  └──────────┘ └──────────┘ └──────────────────┘  │
│  ┌──────────┐ ┌──────────┐ ┌──────────────────┐  │
│  │ 格式转换  │ │ 日志记录  │ │ 计费扣减         │  │
│  └──────────┘ └──────────┘ └──────────────────┘  │
└───────┬──────────────┬──────────────┬────────────┘
        │              │              │
        ▼              ▼              ▼
┌──────────┐  ┌──────────┐  ┌──────────┐
│ OpenAI   │  │ DeepSeek │  │ 通义千问  │
│ upstream │  │ upstream │  │ upstream │
└──────────┘  └──────────┘  └──────────┘
```

核心流程：**用户请求 → Token鉴权 → 查余额 → 匹配渠道 → 格式转换 → 转发上游 → 扣费 → 返回结果**，整个过程对用户透明。

## 三、二次开发的三种玩法

### 玩法1：纯换皮（技术含量 ⭐）

```
Fork 项目 → 改 logo + 标题 + 配色 → 部署 → 上线
```

改 `web/` 目录下的前端页面，换个品牌名就开张。半小时搞定。

### 玩法2：功能增强（技术含量 ⭐⭐⭐）

这才是正经的二开。在 one-api 或 new-api 的基础上：

- **加支付**：对接支付宝当面付、微信支付（原版只有 EPay 和 Stripe）
- **加渠道**：对接新的模型提供商（比如某个新出的国产大模型）
- **加运营功能**：用户邀请返佣、签到送额度、套餐系统
- **自定义计费**：按用户等级设置不同的倍率

### 玩法3：前后端分离重构（技术含量 ⭐⭐⭐⭐）

```bash
前端：LobeChat / ChatGPT-Next-Web 二开
后端：new-api 纯做 API 网关
数据库：MySQL（用户系统 + 订单记录）
缓存：Redis（Token验证 + 限流）
```

这种架构更灵活：前端可以做成任何想要的交互，后端只负责 API 路由和计费。

> ⚠️ **技术声明**：以上所有玩法都以合法获取上游API授权为前提。未经授权代理、转售API可能违反上游服务条款。

## 四、合规红线：做之前必须想清楚的事

这部分不是"免责声明"，是**真实的法律和技术边界**。根据公开信息整理：

### 4.1 国内监管要求

根据《生成式人工智能服务管理暂行办法》：

- 向**中国境内公众**提供生成式AI服务的，**必须完成算法备案**
- 服务提供者需要承担内容安全责任
- 需要建立投诉举报机制

> one-api 的 README 中也明确写了：「请勿对中国地区公众提供一切未经备案的生成式人工智能服务。」

### 4.2 上游服务商的使用条款

| 服务商 | 关键限制 |
|--------|---------|
| OpenAI | 禁止未授权转售API；禁止将输出用于竞争模型训练 |
| Anthropic | 禁止未经书面同意的再分发 |
| DeepSeek | 开放API，但商业转售需查看最新协议 |
| 国内模型厂商 | 通常禁止未授权的密钥转售 |

### 4.3 合法使用场景

one-api / new-api 本身是中立的技术工具，合法场景包括：

- **企业内部统一管理**：公司买了多个模型厂商的API，用one-api做统一入口和成本核算
- **个人学习研究**：自己用，不对外提供服务
- **有授权的中转服务**：与上游厂商签了正式合作协议的B2B服务

## 结语

从技术角度看，one-api → new-api 这条演进线，展示了一个优秀的开源项目如何催化整个细分领域——它把一个"要写几百行适配代码"的问题变成了"docker run 一条命令"。

但从商业和合规角度看，这个领域的门槛从来不在代码层面。真正的难度在于：**合法的上游渠道、稳定的服务质量、以及完整的合规手续。**
