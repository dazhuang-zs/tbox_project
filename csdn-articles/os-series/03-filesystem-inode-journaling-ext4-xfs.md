# 文件系统设计哲学：从 inode 到现代日志文件系统，一文讲透存储层

> 文件系统是操作系统里最「长寿」的组件——你的硬盘很可能比你的 CPU 架构活得久。理解它的设计，就是理解如何让数据在几十年内不出错。

---

## 一、文件系统到底解决什么问题

把文件系统的问题简化到极致：**给定一个名字（如 `/home/user/photo.jpg`），找到它在磁盘上的所有数据块，并保证写入过程不会因为断电而损坏。**

这个看似简单的问题涉及三个核心挑战：

1. **空间管理**——磁盘上哪些块是空闲的？怎么分配新块？怎么回收删除的块？
2. **索引**——文件名怎么对应到磁盘上的数据块？大文件、小文件怎么高效索引？
3. **一致性**——写入过程中断电了怎么办？怎么保证不会出现「数据写了一部分但元数据没更新」的半死状态？

---

## 二、inode：文件系统的身份证

### 2.1 inode 里有什么

在类 Unix 文件系统中，文件的名字和内容不是同一个东西。**文件名存在目录里，文件的一切元数据存在 inode 里。**

一个 inode 包含：

| 字段 | 含义 | 典型大小 |
|------|------|----------|
| 文件类型与权限 | 普通文件/目录/符号链接 | 2 字节 |
| 所有者 UID/GID | 谁拥有这个文件 | 4 + 4 字节 |
| 文件大小 | 字节数 | 8 字节 |
| 时间戳 | atime / mtime / ctime | 3 × 8 字节 |
| 链接计数 | 有多少个文件名指向这个 inode | 2 字节 |
| **数据块指针** | 文件内容在磁盘上的位置 | **核心** |

### 2.2 数据块指针：inode 怎么找到文件内容

inode 本身只有128-256 字节，不能直接存放大量数据。它的方案是间接索引：

```
inode
├── direct[0]  ──→ [数据块]  直接指针 × 12，每个指 4KB = 48KB
├── direct[1]  ──→ [数据块]
├── ...
├── direct[11] ──→ [数据块]
│
├── indirect    ──→ [间接块] ──→ 256 个指针，每个 4KB = 1MB
│
├── double_indirect ──→ [二级间接块] ──→ 256 × 256 × 4KB = 256MB
│
└── triple_indirect ──→ [三级间接块] ──→ 256³ × 4KB ≈ 64GB
```

**这个设计的精妙之处：**

- 小文件（<48KB）：只用直接指针，一次磁盘读取就能拿到数据。
- 中等文件（<1MB）：需要一次额外间接块读取。
- 大文件（<256MB）：需要两级间接。
- 超大文件（<64GB）：需要三级间接。

大多数文件都很小（Richard McDougall 在 2006 年对 Solaris 文件系统的研究中指出，80% 以上的文件小于 10KB），所以大多数文件只需要直接指针，性能最优。

### 2.3 目录怎么存文件名

目录本质上是一个特殊的文件，内容是文件名到 inode 号的映射表：

```
目录 "/home" 的内容：
┌────────────┬─────────┐
│ 文件名      │ inode 号 │
├────────────┼─────────┤
│ .          │ 256     │
│ ..         │ 128     │
│ user       │ 512     │  ← 子目录
│ photo.jpg  │ 1024    │  ← 普通文件
└────────────┴─────────┘
```

所以当你访问 `/home/user/photo.jpg`：
1. 从根 inode（固定 inode 号 2）开始
2. 打开根目录 → 找到 "home" → 拿到 inode 256
3. 打开 inode 256 → 找到 "user" → 拿到 inode 512
4. 打开 inode 512 → 找到 "photo.jpg" → 拿到 inode 1024
5. 打开 inode 1024 → 拿到数据块指针 → 读取数据

每一步都是一次磁盘 I/O。这就是为什么路径解析是文件系统性能的关键路径之一——这也是 dentry cache（目录项缓存）存在的根本原因。

## 三、日志（Journaling）：如何防止断电导致文件系统损坏

### 3.1 问题场景

假设你要给一个文件追加 4KB 数据。这需要三步：

1. 在磁盘上分配一个新的数据块
2. 更新 inode 的数据块指针和文件大小
3. 把数据写到新分配的数据块

如果在这三步之间断电了：

- 1 和 2 完成了，3 没完成 → 文件大小显示增加了，但数据块里是垃圾
- 1 完成了，2 和 3 没完成 → 分配了一个孤儿块（没人引用它，但被标记为已使用）
- 什么恰好完成取决于磁盘缓存的写入顺序，不可预测

传统文件系统（ext2）的解决方案：**fsck**。启动时扫描整个文件系统，检查所有 inode、块位图、目录的一致性。问题是：一个 1TB 的 ext2 文件系统，fsck 可能要跑 **几十分钟**。

### 3.2 日志文件系统的核心思想

日志（journal）是一个循环使用的预留磁盘区域。写入流程变成：

```
1. 先把「我要做什么」写在日志里（写日志）——这个操作很快，是顺序写
2. 再真正执行这些操作（提交到文件系统主区域）
3. 在日志里标记这笔操作「已完成」
```

如果断电后重启：
- 日志里有「未完成」的记录 → 重放（redo），把记录里的操作执行完
- 日志里没有未完成记录 → 文件系统是干净的，不需要 fsck

**关键：** 日志保证了元数据的原子性——要么全部完成，要么全部不做。恢复时间从「扫描整个磁盘」变成「扫描日志区域（几十 MB）」，从几十分钟变成了几秒钟。

### 3.3 三种日志模式

以 ext4 为例，有三种日志模式：

| 模式 | 日志内容 | 性能 | 安全性 |
|------|----------|------|--------|
| `data=journal` | 元数据 + 数据 | 最慢 | 最高 |
| `data=ordered`（默认） | 只日志元数据，数据先于元数据写入 | 中等 | 高 |
| `data=writeback` | 只日志元数据，数据可能后写 | 最快 | 最低 |

**`data=ordered` 是 ext4 的默认选择**——平衡了性能和安全性。元数据确保一致（通过日志），数据确保不丢失（通过先写数据后更新元数据的顺序保证）。

## 四、ext4 vs XFS：两个主流 Linux 文件系统怎么选

### 4.1 ext4

**出身：** ext2 → ext3（加日志）→ ext4（2008），Linux 的「原生」文件系统，最老牌。

**核心机制：**
- 默认 4KB 块大小
- inode 表在创建文件系统时预分配（格式化时就决定了最多多少文件）
- 使用 extent（连续块范围）替代间接块，减少大文件的碎片化
- 延迟分配（delayed allocation）：分配数据块时先不决定物理位置，等真正刷盘时根据缓冲区内容一次性决定最优布局
- 支持最大 1EB 卷，单个文件最大 16TB

**强项：** 小文件性能好，稳定可靠，内核支持最深（毕竟是一家人）。

**弱项：** inode 数量创建时固定，无法动态扩展；并发写入的扩展性不如 XFS。

### 4.2 XFS

**出身：** SGI 在 1994 年为 IRIX 开发，2001 年移植到 Linux。设计目标就是高性能和可伸缩。

**核心机制：**
- 分配组（Allocation Group, AG）：把文件系统分成多个独立管理的区域，并发操作可以在不同 AG 上并行执行
- B+ 树无处不在：inode 分配用 B+ 树、空闲空间管理用 B+ 树、extent 映射用 B+ 树
- 动态 inode 分配：不预分配 inode 表，需要时动态创建（没有「inode 用完了」的问题）
- 延迟分配 + 预分配（speculative preallocation）：对大文件追加写入预先分配一大块连续空间，但只在真正写入时才标记为已使用

**强项：** 大文件写入性能极好，并发扩展性强，inode 数量没有硬限制。

**弱项：** 小文件操作不如 ext4（B+ 树的维护开销），删除后恢复困难（xfs_undelete 能力有限），断电时如果没有 UPS 数据丢失风险比 ext4 高（因为 aggressive caching，不过可以通过挂载选项 `-o sync` 缓解）。

**选择建议：**
- 通用服务器（Web、应用、数据库）→ ext4，够用且最稳。
- 大文件存储（视频、镜像、备份）→ XFS。
- 需要 inode 动态增长 → XFS（ext4 的 inode 数是格式化的硬限制）。

## 五、超级块与块组——文件系统的自我描述

### 5.1 文件系统在磁盘上的布局

```
ext4 磁盘布局：

┌─────────┬─────────┬─────────┬─────────┬─────────┐
│ 超级块    │ 块组0    │ 块组1    │ 块组2    │ ...     │
│ (Block 0)│         │         │         │         │
└─────────┴─────────┴─────────┴─────────┴─────────┘

每个块组：
┌──────────┬──────────┬───────────┬──────────┬─────────────┐
│超级块备份  │组描述符   │块位图      │inode位图  │inode表 + 数据块│
└──────────┴──────────┴───────────┴──────────┴─────────────┘
```

**超级块（superblock）** 是整个文件系统的「身份证」：
- 块大小
- 总块数
- inode 总数
- 空闲块数
- 挂载次数、最后挂载时间、最后检查时间
- 文件系统 UUID

超级块在多个块组中有备份（默认在块组 0、1、3、5、7 的幂次方位置），防止单点故障。

### 5.2 位图（bitmap）

块位图和 inode 位图各是一个比特数组：bit[i]=1 表示第 i 个块/inode 已被使用，bit[i]=0 表示空闲。

分配新文件时：
1. 查 inode 位图找到空闲 inode → 分配
2. 查块位图找到空闲数据块 → 分配
3. 更新两个位图

由于位图非常紧凑（一个字节管 8 个块），一个块组的位图可以放在一个 4KB 的块内。

## 六、VFS：Linux 的「任何文件系统都能用」

Linux 能挂载 ext4、XFS、btrfs、NTFS、FAT32、NFS、tmpfs……几十种文件系统，但上层应用不需要写 `if (ext4) ... else if (xfs) ...`。这归功于 **VFS（Virtual File System，虚拟文件系统）**。

```
应用层     open() / read() / write() / close()
                │
           ┌────▼────────────┐
           │   VFS 层         │
           │ (统一接口)        │
           └────┬──────┬──────┘
                │      │
        ┌───────▼┐ ┌───▼────────┐
        │ ext4   │ │ XFS        │ ...
        │驱动     │ │ 驱动        │
        └────────┘ └────────────┘
```

VFS 定义了四个核心数据结构：

| 结构 | 对应什么 | 生命周期 |
|------|---------|----------|
| `super_block` | 一个挂载的文件系统 | 挂载到卸载 |
| `inode` | 一个文件 | 文件被打开到关闭 |
| `dentry` | 路径中的一个组件 | 缓存在内存中 |
| `file` | 一个打开的文件实例 | 进程打开到关闭 |

`dentry`（directory entry，目录项）缓存尤其重要——它把路径解析的结果缓存在内存中。当你反复访问同一个文件时，只有第一次需要走完整的路径解析，后续直接从 dentry cache 拿到 inode，不需要任何磁盘 I/O。

## 七、动手实验

```bash
# 查看文件系统类型
df -T /

# 查看 inode 使用情况（inode 用完了就不能创建新文件）
df -i

# 查看 ext4 超级块信息
sudo dumpe2fs /dev/sda1 | head -30

# 查看 XFS 信息
sudo xfs_info /

# 查看文件的 inode 号
ls -i /etc/passwd

# 通过 inode 号查找文件
find / -inum 123456 2>/dev/null

# 查看日志大小
sudo dumpe2fs /dev/sda1 | grep -i journal

# strace 追踪文件操作——看看实际发生了什么系统调用
strace -e trace=file cat /etc/hostname
```

## 八、总结

文件系统的设计有三个支柱：

1. **索引结构（inode + 间接/直接指针）**——解决「怎么快速找到文件的所有数据块」
2. **日志（journaling）**——解决「断电后怎么保证一致性」
3. **缓存（page cache + dentry cache + inode cache）**——解决「怎么让重复访问不产生磁盘 I/O」

而 ext4 和 XFS 的选择，本质上是在「稳定性 + 小文件性能」和「伸缩性 + 大文件吞吐」之间做权衡。

理解了这个框架，再去看 btrfs、ZFS、bcachefs 等下一代文件系统（CoW、快照、校验和、压缩、子卷……），你会发现它们只是在旧的三个支柱上各自加了新的楼层——但基础结构没变。
